Operating model

Speed an executive can trust

AI accelerates delivery. These controls keep it safe, reviewable and affordable. Each one answers a concern a leadership team will raise.

Governance

Written spec and AI house rules

One document owns the architecture, scope and phases. Written rules in the repository set what the AI may and may not do.

Quality and auditability

Every change reviewed

A branch and a pull request for each change, with automated tests, a build and a config check before anything merges.

Operational risk

Safe to change

Backups before risky changes, changes that are easy to undo, and notice of what will restart before it does.

Security

Secure by design

Signed device enrollment, per-device encrypted tunnels, roles enforced on the server, HSTS and an enforced content security policy.

Cost

Spend is a design input

Free-tier cloud, a small footprint, work spread across several AI agents, and a public demo that cannot trigger expensive work.

Measurement

Evidence on the record

Commit history, tagged releases and a changelog show what changed, when and why, for anyone who needs to audit it.

Judgment

Decisions and trade-offs

What I chose, why, and what I gave up. Real systems run on architectural discipline, not unchecked complexity.

Emulated an engineering squad across multiple AI tools, coordinated via Git

Why
In the real world, I would lead a team of specialized engineers. Replicating that solo with AI meant being smart about cost and context: leaning on a single model for an entire build burns through expensive tokens and quickly turns code into spaghetti. Instead, I assigned specific features to different AI coding tools on isolated Git branches, using pull requests and strict review rules to keep the work modular and disciplined.
Gave up
The quick convenience of single-prompt "vibe coding." Managing multiple tools through Git takes real operational overhead, but it is the only way to build software that lasts.

Chose portable architecture over familiar cloud ecosystems

Why
It is easy to create accidental vendor lock-in when you build in the clouds you know best. Deploying a clean Docker Compose, Caddy, and PostgreSQL stack on Oracle Cloud forced the architecture to stay strictly portable, proving the entire system can migrate back to AWS, GCP, or bare metal without rewriting code.
Gave up
The muscle memory and familiarity of AWS and GCP, trading the platforms I know inside out to prove true cloud portability.

Designed around edge hardware and residential bandwidth limits

Why
A Raspberry Pi is not an enterprise appliance, and a home broadband connection is not a dedicated corporate circuit. If you fire off parallel bandwidth tests, you will peg the Pi's CPU, choke the uplink, and create the very lag you are trying to measure. Spacing tests out and serializing heavy traces keeps the monitor completely non-intrusive to normal household traffic.
Gave up
Instant, all-at-once telemetry. Heavy tests run in a staggered queue rather than all in parallel.

Simulated the fleet in software instead of building a physical home lab

Why
In an enterprise, a dedicated hardware lab with proper test gear is a must. In a house, turning your living room into a staging rack makes zero sense. Running containerized virtual agents on the server let me stress-test fleet check-ins, network drops, and dashboard load without cabling up a pile of hardware.
Gave up
Real-world RF testing across multiple rooms. Software simulation validates the platform logic, but Wi-Fi attenuation, wall interference, and antenna quirks can only be verified on physical hardware.
Roadmap

Held back autonomous AI operations to avoid runaway inference costs (Phase 2.0)

The plan
Autonomous agents that continuously monitor logs, diagnose dropouts, restart interfaces, and open ISP escalation tickets.
Why not yet
Anyone who has actually built autonomous agents knows they burn through money fast. Having an LLM continuously parse high-volume streaming logs and chain reasoning loops causes massive budget shock in an enterprise, and at home it is financially reckless. Until the telemetry is tightly pre-filtered into lean, deterministic triggers that keep token consumption bounded, 24/7 agentic operations stay on the drawing board.

The project

HomeNetWatch, in production

A Raspberry Pi measures a home network, a cloud server stores the results, and a live dashboard shows where a connection degrades, how hard the server is working, and what the airwaves look like—including a Security tab for wireless alerts and on-demand LAN scans. What this means for an enterprise

What I would measure in a company

This is a hobby project on my home network. It is not an enterprise rollout, and I have not proven any savings. If a company used the same approach, these are the things I would measure.

  • How quickly new infrastructure and internal tools get delivered
  • Whether every change can be traced and reviewed
  • What it costs to run, and how many problems reach production
  • Whether building costs less than buying software with features you never use

What this project produced, as of October 28, 2026: original alpha (v0.2) built in nine days, now at version v0.5 with 125 merged pull requests, 205 automated tests, and 30 of those 125 pull requests were fixes. One person, one project. See the history → A company would also have to count support, patching and compliance.

    One page shows how hard the server is working, how full its disk is, when it would run out of space, and whether its software has known security flaws.

    A Security tab for Kismet WIDS alerts, trust attention and on-demand LAN scans, plus a Server Health table of bytes received and sent over common periods.

  10. Roadmap

    Built from scratch as its own project, RTN_PackGen on GitHub. The G.711 voice test already uses it, and it's headed for an upcoming release.

  11. Roadmap

    In development: it will read through logs and errors quickly, work out what matters, and summarize the alerts in plain language.
